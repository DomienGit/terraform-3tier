● Plan nauki

  Nie rzucamy się od razu na cały 3-tier (2×VPC + TGW + ASG to setki linii i
  pełno płatnych zasobów). Zamiast tego budujemy tę samą architekturę etapami, 
  od najmniejszego kawałka, a przy każdym etapie dochodzi nowy koncept
  Terraforma:

  1. Zadanie 1 (teraz): sieć — VPC, subnety, IGW, tablice routingu → podstawy: 
  resource, variable, output, state, plan/apply/destroy
  2. Security groups + bastion EC2 → data sources, user_data, key pair
  3. RDS MySQL (free tier) → db_subnet_group, zależności między zasobami
  4. S3 + IAM role + alarm CloudWatch → IAM w Terraform, enkle mechanizmy
  5. ALB + Auto Scaling Group → launch template, najbardziej "zapętlony" 
  fragment
  6. Refaktor na moduły + remote state w S3 → to, co spotykasz w prawdziwych 
  repo

  Zadanie 1: fundament sieciowy 3-tier

  Krok 0 — narzędzia (zanim dotkniesz Terraforma):
  - Zainstaluj Terraform (hashicorp ma oficjalne repo APT dla Debiana/Ubuntu) i
  AWS CLI v2
  - aws configure — klucze z Twojego konta, region np. eu-central-1 (Frankfurt,
  blisko i tani)

  Krok 1 — katalog projektu. Załóż projekty/terraform-3tier/ z osobnym repo gita
   (to będzie portfolio) i taką strukturą plików — nie jednym plikiem, od razu
  ucz się porządku:

  terraform-3tier/
  ├── versions.tf    # provider aws + required_version
  ├── variables.tf   # region, cidr VPC
  ├── main.tf        # zasoby
  ├── outputs.tf
  └── .gitignore     # .terraform/ i terraform.tfstate*

  Krok 2 — co ma powstać (miejska wersja sieci z Twojego projektu, bez drugiego
  VPC i TGW):

  - VPC 10.0.0.0/16 z tagami Name i Project
  - 2 publiczne subnety (np. 10.0.1.0/24, 10.0.2.0/24) w dwóch różnych AZ
  - 2 prywatne subnety (10.0.11.0/24, 10.0.12.0/24) też w dwóch AZ
  - Internet Gateway + tablica routingu z trasą 0.0.0.0/0 → IGW, powiązana z
  publicznymi subnetami
  - Osobna tablica routingu dla prywatnych subniet (bez NAT Gateway — patrz
  koszty), przypisana do nich

  Wymagania "terraformowe":
  - CIDR i region jako variables
  - Outputs: vpc_id oraz lista ID publicznych subniet
  - Bonus dla ambitnych: zamiast 4 kopiuj-wklej bloków subneta spróbuj for_each
  — porównaj oba podejścia

  Krok 3 — obowiązkowy workflow (dokładnie w tej kolejności, zawsze):

  terraform init → fmt → validate → plan → apply → (sprawdź w konsoli AWS) →
  destroy → (sprawdź, że zniknęło)

  Przy plan przeczytaj cały output zanim powiesz yes — naucz się czytać, co
  Terraform zamierza stworzyć. Definition of done: apply przechodzi, w konsoli
  widzisz VPC z 4 subnetami i tablicami, destroy sprząta wszystko, a Ty umiesz
  odpowiedzieć na pytania kontrolne poniżej.

  Pytania kontrolne (odpowiesz mi na następnej sesji, jak na rozmowie)

  1. Skąd Terraform wie, co już istnieje na AWS i co trzeba stworzyć? Co jest w

  4. Po co komu outputs, skoro wszystko widać w konsoli?

● Gita masz, gh (GitHub CLI) nie — pokażę obie drogi. Sytuacja "mam już pliki,

  Opcja A: przez GitHub CLI (polecam, załatwiasz wszystko z terminala)

  # 1. zainstaluj gh (oficjalne repo GitHub dla apt jest na ich stronie)
  # 2. jednorazowa konfiguracja — otworzy przeglądarkę do zalogowania

  gh repo create terraform-3tier --public --source=. --push

  gh repo create --source=. --push za jednym razem: tworzy repo na GitHubie,
  dodaje je jako origin i wypycha.

  Opcja B: klasycznie przez przeglądarkę

  1. Na github.com: New repository → nazwa np. terraform-3tier → ** UWAGA: NIE
  zaznaczaj** "Add a README / .gitignore / license" — repo ma być puste, inaczej
   pierwszy push odbije się o konflikt (Twój lokalny commit vs. ich README)
  2. W terminalu:

  cd projekty/terraform-3tier
  git init
  git add .
  git commit -m "Initial commit: network setup for 3-tier project"
  git branch -M main
  git remote add origin git@github.com:TWOJ_LOGIN/terraform-3tier.git
  git push -u origin main

  Przy git remote add adres z HTTPS (https://github.com/...) też działa, ale
  wtedy przy każdym pushu pyta o hasło/token. SSH (git@github.com:...)
  wygodniejsze na dłuższą metę — wymaga wygenerowania klucza i dodania go na
  GitHubie.

  Dwie pułapki konkretnie w Twoim przypadku

  1. Upewnij się, że .gitignore istnieje ZANIM zrobisz git add . — inaczej
  wrzucisz terraform.tfstate i katalog .terraform/ (setki MB). Po git add .
  sprawdź jeszcze git status, czy nie dociągnęło się coś podejrzanego. State
  file prędzej czy później zawiera sensitive dane, a z publicznego repo nie da
  się nic trwale usunąć — GitHub trzyma historię commitów.
  2. Jak już omyłkowo coś dodałeś: git rm --cached terraform.tfstate (usuwa z
  indeksu, nie z dysku) + commit.

  A gdyby push odepchnął błędem, bo repo jednak nie było puste — nie rób push 
  --force, tylko: git pull --rebase origin main i dopiero potem push.

● Dobra obserwacja — i dobra wiadomość: to bezróżnicowe dla Terraforma. Nazwa
  pliku to tylko konwencja.

  Jak to działa

  Terraform ładuje wszystkie pliki *.tf z katalogu i scala je w jedną
  konfigurację. Nie obchodzi go, czy blok terraform {} siedzi w terraform.tf,
  versions.tf czy main.tf — ważne, żeby blok był w projekcie jeden.

  Nazwa to czysta czytelność dla ludzi. Spotykane konwencje:

  ┌──────────────┬───────────────────────────────────────────────────────────┐
  │     Plik     │                      Skąd się wziął                       │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ terraform.tf │ oficjalne tutoriale HashiCorp — dlatego to widzisz w docs │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ versions.tf  │ popularna konwencja w prawdziwych projektach i modułach   │
  ├──────────────┼───────────────────────────────────────────────────────────┤
  │ main.tf      │ szybkie tutoriale, wszystko w jednym pliku                │
  └──────────────┴───────────────────────────────────────────────────────────┘

  Moja rada: skoro uczysz się z oficjalnej dokumentacji, trzymaj się jej —
  nazwij plik terraform.tf i konsekwentnie tego używaj. Ja podałem versions.tf,
  bo to częste w repo produkcyjnych, ale w tym momencie mniejsza o to — wybierz
  jedno i nie mieszaj.

  Jedno ważne rozróżnienie, żeby się nie pomylić

  To dwa różne bloki, które łatwo ze sobą pomylić:

  # terraform.tf — "co instalować"
  terraform {
    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 5.92"
      }
    }
    required_version = ">= 1.2"
  }

  # provider.tf albo main.tf — "jak się skonfigurować"
  provider "aws" {
    region = var.aws_region
  }

  - terraform { required_providers } — deklaruje, że używasz providera AWS i w
  jakiej wersji. Nic nie łączy się z AWS.
  - provider "aws" {} — faktyczna konfiguracja: z jakiego regionu i jakimi
  credentials Terraform będzie rozmawiał z AWS. Ten blok też będzie ci
  potrzebny.

  Oba potrzebujesz. Pytanie rekrutacyjne z tego tematu: "czemu w ogóle przypinać
   wersje providera?" — bo provider AWS zmienia się co tydzień i bez przypięcia
  terraform init na innym komputerze (albo na runnerze CI za rok) może ściągnąć
  inną wersję, która zachowuje się inaczej. Version constraint to冻结 składni.

  A znak ~> 5.92 znaczy: "5.92 lub nowszy, ale poniżej 6.0" (tzw. pessimistic
  constraint — wersja minor i patch mogą rosnąć, major nie).
